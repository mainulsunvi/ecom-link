# Spec 006: AI Content Assist

Status: MVP. Feature: `docs/FEATURES.md` M7.

## 1. Problem statement

Synced WooCommerce products often have empty short descriptions and missing SEO fields, which leaves Framer pages looking unfinished. The merchant needs AI-generated drafts for those fields, reviewable and editable before applying, without ever overwriting the store's own data.

## 2. Data model decision

- CMS fields (new, optional in the recommended schema): `seo_title`, `seo_description`. The short description maps to the existing Woo field but is treated as an AI target only when its direction is one-way and the merchant invokes AI explicitly.
- `AiSettings` in plugin data: `{ enabled: boolean }`. Read path: dashboard reads to show the entry point. Write path: Switch toggle persists.
- Drafts are component state only until applied; nothing is written to Woo ever, and CMS writes happen only on "Apply".

## 3. Platform API operations

None to WooCommerce. Generation runs through the Framer plugin AI capability where available; no external AI keys in v1 (research section 15). If no capability exists at implementation time, the spec falls back to disabled-by-default with the entry point hidden: flagged as a blocking open question.

## 4. Credentials required

None beyond the existing connection. No `framer.json` change.

## 5. Triggers consumed

User actions: "Generate missing content" per item, "Generate for all empty" for the filtered set, edit draft, "Apply".

## 6. File-by-file change list

- `src/ai/contentAssist.ts`: detection of empty targets, draft generation call, apply logic (CMS field writes only), new.
- `src/views/Dashboard.tsx`: AI entry point and empty-content counter, extend.
- Review modal (inside `Dashboard` or `AiReviewModal.tsx`): editable drafts, apply/cancel, new.
- `src/views/SettingsModal.tsx`: AI enable/disable Switch with transparency note, extend.
- `docs/help/AI Content Assist.md`: new, same run.

## 7. Acceptance criteria

1. Given 40 synced items where 12 have an empty short description, the entry point shows "12 items need content."
2. Given generation for the set, drafts open in the review modal with every draft editable before applying.
3. Given "Apply", only AI target CMS fields are written; a mock Woo transport asserts zero outgoing Woo requests during the AI flow.
4. Given AI disabled in settings, the entry point is hidden and generation calls are impossible.
5. Given a Woo field that is mapped two-way, AI never targets it (guard test).
6. The transparency note "Content is generated by AI. Review before publishing." appears in settings next to the Switch.
7. All strings pass the UX writing rules test.

## 8. Open questions

- **Blocking**: confirm the exact Framer plugin AI surface in `@framer/plugin` v4 (availability, quotas, model transparency text). If absent, this spec reduces to a stub and the Orchestrator must be told before build.
- Batch size for "generate for all empty" to avoid long waits: proposed 10 with progress.

## Always answer these four

- **Removed then re-added plugin**: AI settings are lost; applied content stays in CMS because it is data, not plugin state.
- **Framer plan limit mid-sync**: AI writes update existing items, so item limits do not apply.
- **Partial sync failure and retry**: a failed generation leaves drafts untouched; retry regenerates only the failed drafts.
- **Unusually large catalog**: batch cap with progress; the merchant can cancel between batches.
